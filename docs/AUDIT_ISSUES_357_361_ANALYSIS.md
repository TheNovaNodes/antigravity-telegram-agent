## 🔬 2. Детальный разбор каждого тикета

### ❌ Issue #357: Маршрутизация «Rich Article First» и детектор Markdown
* **Суть предложения:** Снизить порог переключения ответа в режим «Статьи» (Tier 2) с 3000 до 1500 символов, если в тексте есть списки или заголовки.
* **Почему это надуманно («натянуто на глобус»):**
  * Лимит стандартного сообщения в Telegram составляет **4096 символов**.
  * Ответ на 1500–2500 знаков со списками и кодом превосходно и компактно читается в обычном пузыре Telegram без каких-либо обрезаний.
* **Почему это СЛОМАЕТ UX (User Experience):**
  * В режиме стриминга бот выводит ответ в реальном времени, редактируя живой черновик (`activeMsgID`).
  * Переход в Tier 2 (Rich Article) **атомарно удаляет стриминговое сообщение** и отправляет новое с нуля (`delMsg := tgbotapi.NewDeleteMessage(...)`).
  * Если опустить порог до 1500 знаков, **каждый второй ответ модели будет визуально исчезать из чата и пересоздаваться**, вызывая постоянное мерцание (flicker) и сбивая чтение пользователя.
* **Вердикт:** 🔴 **REJECT**. Текущий порог в 3000 символов выверен и оптимален.

### ❌ Issue #358: Ликвидация утечки SSH_AUTH_SOCK, санитизация экспорта и SAST
* **Суть предложения:** Убрать `SSH_AUTH_SOCK` из переменных дочерних процессов, санитизировать транскрипты по регулярке, убрать `.*` из `.gosec.json`.
* **Почему это надуманно:**
  * **Фантом SSH:** Проверка реального запущенного сервиса на проде показала:
    ```bash
    cat /proc/$(pgrep antigravity-bot | head -n 1)/environ | tr '\0' '\n' | grep SSH
    ```
    Переменной `SSH_AUTH_SOCK` **нет в окружении демона**. Никакой утечки ключей на проде не происходит.
* **Почему это СЛОМАЕТ продакшен и CI:**
  1. **Смерть GitHub Actions CI:** Файл `.gosec.json` сейчас содержит `path: ".*"`. Если его убрать, запуск `make sast` в CI упадет с сотнями алертов на совершенно легитимный код (вызовы `os.Open`, `exec.Command` для `agy`, неперехваченные ошибки логов). **Все PR перестанут проходить проверки.**
  2. **Искажение кода разработчиков:** Предложенная регулярка для паролей:
     `(?i)(password|secret|token|api[_-]?key)\s*[:=]\s*...`
     слепа к контексту программирования. В экспортируемом диалоге любой нормальный код:
     ```go
     token := generateToken()
     password := hashPassword(str)
     ```
     превратится в кашу из `[REDACTED_SECRET]`.
* **Здоровое зерно:** Единственное полезное замечание — убрать расширение `.env` из авто-отправки текстовых артефактов в `session.go:1073`.
* **Вердикт:** 🔴 **REJECT**. Закрыть. Точечный запрет отправки `.env` перенести в #359.

### ✅ Issue #359: Утечка аккаунтов в /usage, предохранитель БД и экранирование
* **Суть предложения:** Починить зависание аккаунтов в `/usage`, предотвратить сброс всей базы сессий, экранировать спецсимволы Telegram.
* **Реальность проблем (100% реальные баги продакшена):**
  1. **Зависание аккаунта в `/usage` ([`handlers.go:451`](file:///root/projects/TheNovaNodes/antigravity-telegram-agent/handlers.go#L451)):**  
     Хэндлер вызывает `GlobalAccountPool.AcquireAccount(...)`, выставляя `acc.State = StateInUse`, но никогда не вызывает `ReleaseAccount`. Аккаунт «утекает» и считается занятым.
  2. **Глобальный дроп базы данных ([`account_handlers.go:27-31`](file:///root/projects/TheNovaNodes/antigravity-telegram-agent/account_handlers.go#L27-L31)):**  
     При вызове функции с `userID == 0` выполняется:
     ```go
     db.Exec("UPDATE users SET session_id = NULL")
     ```
     Это стирает сессии **всех пользователей бота во всей базе данных**!
  3. **Ошибки Telegram API (400 Bad Request):** Вставка `sessionTitle` и `acc.Email` без экранирования `_`, `*`, `<`, `>` периодически ломает Telegram Bot API.
* **⚠️ ВНИМАНИЕ: Ошибка в самом ТЗ #359 (Предотвращение поломки базы данных):**
  * В ТЗ написано: *«заменить на `UPDATE users SET session_id = NULL WHERE chat_id = ?`»*.
  * **Фактическая схема таблицы `users` ([`storage.go:269-275`](file:///root/projects/TheNovaNodes/antigravity-telegram-agent/storage.go#L269-L275)):**
    В таблице есть только `user_id INTEGER PRIMARY KEY`. **Колонки `chat_id` там нет!**
  * Если билдер выполнит ТЗ буквально — база данных в рантайме вызовет `no such column: chat_id`.
  * **Корректный фикс:** Если `userID == 0`, базу данных вообще не трогать (no-op + warning log).
* **Вердикт:** 🟢 **VALID (с обязательной корректировкой SQL-логики)**. Это единственный тикет, необходимый продакшену.

### ❌ Issue #360: Асинхронная персистентность пула аккаунтов
* **Суть предложения:** Сделать асинхронный воркер с дебаунсом для сохранения файла `accounts.json`.
* **Почему это надуманно (Cargo Cult Architecture):**
  * В реестре `/etc/antigravity-bot/accounts/accounts.json` сейчас всего **10 аккаунтов**. Размер файла — **14 КБ**.
  * Время атомарной записи 14 КБ на NVMe диск — **менее 0.2 миллисекунды**.
  * Городить асинхронный бекграунд-процесс с таймерами и очередями ради экономии 0.2 мс — это классическая преждевременная оптимизация.
  * Асинхронная запись создает риск потери актуального состояния пула при внезапном сбое процесса (`SIGKILL` / падение контейнера).
* **Здоровое зерно:** Защита `NewAccountPool` от перезаписи файла пустым состоянием при битом JSON (режим Fail-Closed). Но для этого не нужны асинхронные воркеры.
* **Вердикт:** 🔴 **REJECT**.

### ❌ Issue #361: Базовая изоляция процесса демона в systemd
* **Суть предложения:** Включить `PrivateTmp=true`, `ProtectKernelTunables=true`, `ProtectControlGroups=true` в systemd-юните.
* **Почему это надуманно и СЛОМАЕТ воркфлоу:**
  * Наш бот — это **административный DevOps-ассистент под `root`**, развернутый на выделенном сервере инфраструктуры.
  * Он запускает дочерние агенты `agy`, которые работают с Docker, сокетами, компилируют софт, читают системные метрики и взаимодействуют с сервисами хоста.
  * Включение `PrivateTmp=true` изолирует `/tmp` в приватное пространство имен. Агент перестанет видеть сокеты и временные файлы хоста.
  * `ProtectKernelTunables` и `ProtectControlGroups` заблокируют системные диагностические команды, которые ЗавЛаб регулярно поручает боту.
* **Вердикт:** 🔴 **REJECT**.
