# Architecture Decision Record: Bounded Autonomous Engineering Loop

## 1. Problem
Currently, autonomous coding agents operate under the dangerous assumption that their own evaluation of success equates to system success. There is no isolated, multi-layered verification system that prevents an agent from hallucinating fixes, deleting tests to pass CI, or pushing destructive changes directly to production environments.

## 2. Goals
- Define a Bounded Autonomous Engineering Loop where the agent can experiment and repair code autonomously, but cannot bypass objective verification.
- Establish strict trust boundaries and a precise Git safety workflow.
- Ensure the LLM never grades its own success.

## 3. Non-goals
- Creating a completely unguided "AGI" coder.
- Deploying changes directly to production without human or strict CI policy approval.
- Using the LLM to write or alter protected test suites.

## 4. Candidates
- **A. Reflexion Loop (Agent -> Fix -> Agent Eval):** Rejected. The agent is the sole arbiter of truth, leading to false positives and test-cheating.
- **B. Test-Driven Agent Loop:** Conditional. Useful for implementation, but lacks sandbox isolation and external CI safety nets.
- **C. Self-Healing CI (GitHub -> Agent -> PR):** Rejected as a standalone solution due to high latency, cost, and lack of immediate local agent feedback.
- **D. Jules Repair Loop:** Conditional. Excellent as a secondary intelligence layer, but adds orchestration complexity if used as the primary loop.
- **E. Bounded Autonomous Engineering Loop (Agent -> Sandbox -> Tests -> Verification -> PR):** Approved. Combines local rapid iteration with objective, protected verification boundaries.

## 5. Decision
**Recommended Architecture: Bounded Autonomous Engineering Loop (Candidate E)**
The agent operates within a restricted sandbox. Success is determined strictly by external, protected tests. Changes are proposed via Pull Requests rather than direct merges. 

## 6. Trust Boundaries
`USER (Highest Trust)` -> `ORCHESTRATOR` -> `AGENT (Untrusted Actor)` -> `CODE (Mutable)` -> `TESTS (Protected/Objective)` -> `GIT (Versioned)` -> `CI (Gatekeeper)` -> `PRODUCTION (Zero Trust to Agent)`.

## 7. Security Model
- **Permissions:** 
  - *Read:* repository, logs, tests, CI output.
  - *Write:* source, documentation.
  - *Restricted:* secrets, credentials, infrastructure, production, protected tests.
- **Data Separation (Prompt Injection Defense):**
  - `SYSTEM POLICY` (Immutable constraints) -> `AGENT INSTRUCTIONS` (Task) -> `UNTRUSTED DATA` (Logs, test output). Untrusted data is never parsed as instruction.
- **Change Sensitivity:**
  - *SAFE:* Docs, formatting.
  - *REVIEW REQUIRED:* App logic, dependencies.
  - *HUMAN REQUIRED:* Secrets, Auth, Networking, Deployments.

## 8. Failure Model
- **Loop constraints:** MAX_RETRIES = 3.
- **Failure Fingerprinting:** If Attempt N yields the exact same stack trace / error hash as Attempt N-1, the loop terminates early.
- **Termination Conditions:** Max retries reached, token budget exceeded, sensitive file modified, infrastructure error, or same failure repeated.

## 9. Sandbox
Agents must not execute repairs on the active production filesystem. All repairs are executed in a **Temporary isolated Git worktree** or an **ephemeral Docker container**. If the repair succeeds, a patch is extracted and applied to a staging branch.

## 10. Git Workflow
`main` -> `isolated agent branch` -> `agent patch` -> `protected tests` -> `commit` -> `Pull Request` -> `CI` -> `Human Review` -> `Merge`.

## 11. Verification
- **Protected Tests:** A separate suite of read-only integration/E2E tests that the agent cannot modify. 
- **Rule:** `Agent says SUCCESS != System SUCCESS`. `Tests GREEN == Candidate SUCCESS`.

## 12. Rollback
If the loop terminates with failure, the temporary worktree is destroyed, and the primary branch is completely unaffected. 

## 13. Observability
Full audit trail: Task ID, Failure Fingerprint, Agent Diagnosis, Attempt #1 Diff, Test Results, Final Decision.

## 14. Cost Controls
- MAX_RETRIES = 3
- MAX_FILES = 5 (per repair iteration)
- Token budgets and timeout caps (e.g. max 15 minutes of wall-clock time per repair session).

## 15. Open Questions
- Can Jules serve as a cross-verification reviewer for PRs generated by the local Telegram Agent?
- Can we employ smaller models for diagnostic extraction to reduce token costs before sending the core issue to the reasoning model?
